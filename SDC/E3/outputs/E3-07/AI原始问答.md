# E3-07 AI 原始问答（修复前）

## 本次提问

工具：Codex 编码代理。日期：2026-11-05。

> 项目：Spring Boot 3.5 / JDK 17 的 mall-portal。目标方法是 `UmsMemberReceiveAddressServiceImpl.update(Long id, UmsMemberReceiveAddress address)`。基线在 `defaultStatus=1` 时先清当前会员所有默认地址，再按 `memberId + id` 更新目标；目标不存在或属于其他会员时，目标更新为 0 行，但原默认已被清空。规格要求无效目标返回 0 且发生任何写入前就返回；有效目标保持“先清后更新”；保留接口上的 `@Transactional`，不改 Mapper 生成代码和 HTTP 接口。请只在这个范围内分析：
>
> 1. 解释红线为什么是业务断言失败，而不是事务回滚能解决；
> 2. 给出两种最小候选修复，比较改动位置、写入次数、对相邻行为的影响；
> 3. 推荐一种，并明确哪些结论尚未核实。

## AI 原始回答

根因不是“更新失败后没有回滚”，而是两次写操作中第一次已经成功：基线第 57 行先把当前会员的默认地址清掉，第 59 行才更新目标；无效目标只是让第二次更新的影响行数为 0，方法仍正常返回 0，`@Transactional` 不会因为正常返回值而回滚。因此必须让无效目标在第一次写之前退出。

候选 A：在第 44–45 行构造好 `memberId + id` 的 `example` 后，先用 `addressMapper.selectByExample(example)` 查目标是否存在；为空就返回 0。改动约 3 行，复用现有查询条件和 `CollectionUtils` 依赖，成功路径的两次写入顺序完全不变。代价是每次更新多一次 SELECT。

候选 B：先执行目标更新，只有返回 1 才清除其他默认；为了避免把目标自己清掉，还必须在清理条件中排除目标 id。该方案仍要先写目标，再写默认标记，且要引入 `andIdNotEqualTo` 或额外查询；对“已是默认”的地址还要特别处理。改动和相邻行为风险都比 A 大。

候选 C：依赖异常或手动事务回滚。该方案改变返回协议，且当前无效目标是正常返回 0，不适合作为本规格的最小修复。

推荐 A。A 把“目标属于当前会员”作为写入前的前置条件，保持既有会员过滤、成功路径顺序和事务声明；B 的写入语义更复杂，C 改变调用协议。

尚未核实：A 在实际 Mapper/MySQL 上的查询与提交行为；HTTP 入口；并发下两个请求同时设默认；这些不能从单元测试推断。需要用同一组规格测试的改前红灯和改后绿灯，并对相邻的普通更新、已默认、未传默认状态做回归；还应记录失败路径经过新增的返回语句，以及覆盖率的局限。

## 人工核对后的采纳/驳回

- 采纳 A。改前 `SDCE307StudentTest` 两例红，改后 6 例全绿；第 46 行查询、第 47 行返回均被覆盖。人工保留原有 `@Transactional` 与“先清后更新”，只加 3 行。
- 驳回 B。没有把目标更新提前；现有测试锁定了有效目标的两次写入顺序，B 会扩大改动和相邻行为风险。
- 驳回 C。没有把返回 0 改成异常，调用协议不变。
- 核实方式：基线红灯、同组绿灯、受控把第 47 行临时改成 `return 7`（两例变为 expected 0 / actual 7），以及 JaCoCo 行/分支覆盖和测试文件哈希。不能据此声称真实数据库、HTTP 和并发已经验证。
