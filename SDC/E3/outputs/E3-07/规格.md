# E3-07 规格：无效地址更新不得清空已有默认地址

## 用户故事

作为已登录会员，我修改自己的收货地址并把它设为默认；如果目标地址不存在或不属于我，系统应拒绝这次修改，且我原来的默认地址必须保持不变。

## 既有契约（修改前确认）

1. 入口：`UmsMemberReceiveAddressController.update`（`mall-portal/src/main/java/com/macro/mall/portal/controller/UmsMemberReceiveAddressController.java:50-55`）调用服务并把返回行数映射为成功或失败响应。
2. 服务：`UmsMemberReceiveAddressService.update`（`mall-portal/src/main/java/com/macro/mall/portal/service/UmsMemberReceiveAddressService.java:29-30`）保留 `@Transactional`。
3. 实现：`UmsMemberReceiveAddressServiceImpl.update`（`mall-portal/src/main/java/com/macro/mall/portal/service/impl/UmsMemberReceiveAddressServiceImpl.java:41-60`）用 `memberId + id` 限定当前会员的目标地址；默认状态为 1 时先清当前会员原默认，再更新目标。
4. 持久化：只使用既有 `UmsMemberReceiveAddressMapper.updateByExampleSelective`，不改表结构、Mapper 生成代码或 Controller 返回协议。

## 验收准则

- AC-1：`id` 不存在时，`update(id, request)` 返回 0，且不调用任何写操作。
- AC-2：`id` 对应地址属于其他会员时，查询条件必须仍包含当前会员；返回 0，且不调用任何写操作。
- AC-3：有效且属于当前会员的非默认地址设为默认时，先清当前会员原默认，再更新目标，返回目标更新行数。
- AC-4：已是默认的地址再次更新、普通字段更新、未传 `defaultStatus`（按 0 处理）时，保持原有语义。
- AC-5：不得为了修复无效目标而放宽会员过滤，不得删除 `@Transactional`，不得改变成功路径的“先清后更新”顺序。

## 业务不变量

- 对同一当前会员，一次有效“设为默认”操作结束后至多保留一个默认地址。
- 无效目标请求是失败的读语义：返回 0，但不产生任何数据库写入，因此不能通过“先写后回滚”实现。

## 非目标

- 不新增数据库唯一约束或并发控制。
- 不改变新增、删除、查询地址的规则。
- 不改变 HTTP 接口和成功响应码。
